R2-D2 Redux · v2 · companion to the main page

Learn the robot,
then reproduce it.

A two-storey house is the hardest cheap-robot problem: stairs you cannot roll up, floors that look identical to a planar scanner, and a budget that rules out the sensors which would make it easy. This page explains how this stack answers that, with simulations you can drive in the browser and a route to running it yourself.

Every number on this page is read from robot_params.yaml — the same file the URDF, the Gazebo world and the navigation layer are built from. The diagrams are generated, and CI fails if they drift from the code.

00 — START HERE

What is real, and what is not

The most useful thing this page can tell you first is what it cannot show you.

Verified

The maths and the wiring

275 unit tests, a climb-envelope analysis against the expanded URDF, and eleven static checkers — parameters, SQL, launch files, Nav2 plugin names, sensor bridging, agent tool contracts. All run in CI on every push.

Partly

The interfaces

The MCP server loads against the real SDK with all 15 tools intact. The URDF expands through xacro. The VLA request shape matches NVIDIA's API. None of it has been driven by a live robot.

Not run

The robot

Nothing here has been simulated or built. Whether the cluster tracks a real staircase is open, and no amount of static analysis settles it. That is the first thing you will find out, and the first thing worth contributing.

What is recorded here, and what is not. The three videos in 07 Demos are screen recordings of the browser simulations on this page, captured with a headless Chromium. They are real recordings of real code — the same constants, the same equations — but they are recordings of arithmetic, not of a robot. There is no Gazebo footage, because the machine this was built on has no simulator and no GPU. Nothing on this page is a re-enactment: the five empty slots stay empty until someone runs the thing. Which is the point of section 07.

01 — THE PROBLEM

Four constraints that fight each other

Each one is easy alone. Together they eliminate almost every obvious design.

Stairs

A differential-drive robot cannot climb a step taller than roughly its wheel radius. A 150 mm residential riser needs a 300 mm wheel, which will not fit under a robot that also has to pass through a 900 mm doorway.

Two floors that look alike

The bedroom sits directly above the kitchen. One occupancy grid fuses them into nonsense, so the map has to be a stack — and something has to know which layer the robot is on.

Low cost, few sensors

One 2-D LiDAR, one IMU, four ToF beams, one camera — about US$150 of sensing. No depth camera, no 3-D LiDAR. A planar scanner is completely blind to the floor it is driving over.

Low compute

Everything on-robot has to run on a Raspberry-Pi-class board in real time. That rules out the heavy controllers and the dense traversability pipelines that would otherwise solve the terrain problem.

The choice that unlocked it

Four tri-star wheel clusters: a triangular carrier with three small wheels at its corners. On flat ground the sub-wheels turn and the carrier is held still — it behaves exactly like an ordinary wheel. On a step, the sub-wheels lock and the whole carrier tumbles over the riser.

The reason this beats a legged design here is not climbing ability. It is that a tri-star rover is still a differential drive at the /cmd_vel level. Nav2, slam_toolbox, the laser scan matcher and the existing ESP32 firmware all keep working untouched. The stair capability is bought entirely in the mechanism plus one transmission switch.

DesignMotorsClimbs stairsKeeps diff-drive kinematicsCost
Differential drive2NoYesLow
Rocker-bogie6Poorly — riser too tallYesMedium
RHex-style whegs6YesNo — needs a phased gaitMedium
Tracks with flippers4+YesYesHigh
Tri-star clusters4YesYesLow

The tri-wheel and star-wheel stair-climbing literature is the source for the mechanism and for the constraint that governs it: cluster reach must exceed the riser, and tread must exceed the sub-wheel diameter.

02 — GEOMETRY

The two inequalities that decide everything

Whether this platform climbs a given staircase is not a matter of tuning. It is settled by two inequalities, before any code runs. 

# 1. Reach must exceed the riser, or no sub-wheel can get onto the step.
reach = cluster_circumradius + sub_wheel_radius
      = 0.115 + 0.050  =  0.165 m   vs a 0.150 m riser  →  10% margin

# 2. Tread must exceed the sub-wheel diameter, or a cluster bridges
#    two risers instead of landing on the tread.
tread = 0.280 m  >  2 x 0.050 = 0.100 m   ✓ 180 mm of landing room

Drag the sliders below. The verdict updates live, and it is the same arithmetic scripts/analyse_climb.py runs in CI — including the third quantity, gait match, which is the one this design does not satisfy cleanly.

Simulation 1 · Climb envelope

A tri-star cluster meeting a step. Amber arc is the reach the cluster can actually get a wheel onto.

Try this: set the riser to 200 mm — a steep old staircase. Reach fails, and no amount of software fixes it. Now raise the cluster radius until it passes, and watch the peak torque climb with it. That trade is why this robot is the size it is.

Where the numbers live on the robot

The bug this geometry hid

A three-spoke carrier has two rest positions, and the difference between them is larger than the step the robot is trying to detect. The first version of the controller held the carriers at zero velocity, which parks them at whichever one they happened to reach.

The fix is a position servo onto the straddle phase, wrapping the error to the carrier's 120° symmetry so it never turns more than 60° to settle. It was found by analyse_climb.py, not by reading the code — which is the pattern for almost every bug in this project.

03 — TERRAIN

Seeing the floor with US$12 of sensing

A 2-D LiDAR sweeps one horizontal plane. It cannot see a step, a threshold, or the edge of a landing. Four downward Time-of-Flight beams can — if you do the trigonometry honestly. 

# On level ground a beam angled `tilt` below horizontal returns a constant:
r_flat  = h / sin(tilt)  = 0.1675 / sin(30°)  = 0.335 m
spot    = h / tan(tilt)  = 0.1675 / tan(30°)  = 0.290 m ahead

# A step shortens the return; a drop lengthens it. The implied height change:
dz = h - r * sin(tilt + pitch)
That pitch term is not optional. On the 12.1° ramp in the test house the robot pitches nose-up, lengthening every return. Without the correction that reads as a continuous cliff, and the robot refuses to use the ramp at all. There is a regression test named for exactly this.

Simulation 2 · What the beam sees

Move the floor under the beam and watch the classification. Then add body pitch and watch the naive reading break while the corrected one holds.

The four outcomes

Why the beams are angled 30°, not 45°: at 45° the spot lands 60 mm ahead of the sensor — inside the robot's own footprint, far too late to react. At 30° from a 167.5 mm mount it lands 290 mm ahead, roughly one cluster-diameter of warning. That distance is also what sets the descent creep, which is the only thing standing between the robot and the bottom of the stairs.

04 — THE CLIMB

Two transmission modes, and the moment between them

The whole stair capability is one switch — and the hardest part is knowing when to throw it.

ROLLING

Sub-wheels driven, carriers held at the straddle phase. Contact radius is 50 mm. Behaves as an ordinary wheel.

Wheel odometry is valid.

TUMBLING

Carriers driven, sub-wheels locked. The contact point walks around the carrier as it rotates over the riser.

Wheel odometry is meaningless — there is no fixed contact radius.

That second line drives a surprising amount of the rest of the stack. The controller publishes /odom_wheel with a covariance of 1e6 and a valid: false flag rather than a plausible number the EKF would happily fuse. The odometry supervisor drops the scan matcher too — a planar scanner pitched 28° up a staircase is looking at the ceiling and returns confident, wrong matches. What is left is dead reckoning on an IMU, which is why the floor manager re-seeds the pose at the head of the flight on arrival.

The trigger that could never have fired

The first version switched into tumbling when body pitch exceeded a threshold — on the reasoning that the front clusters lifting is what starting a climb looks like. But with the carriers phase-locked they cannot lift. A sub-wheel meeting a riser face stalls the robot; the chassis stays level. The threshold never fired, the approach ran its full 15 s timeout driving into the step, and the FSM aborted. The robot would not have climbed one stair.

The signal that does work is the stall itself. Wheel odometry is valid in rolling mode, so contact is declared when both front beams see a riser and achieved travel stays below 35% of commanded for 0.6 s. Both halves matter: a stall alone fires on a chair leg or a rug; riser-ahead alone fires while the robot is still a lookahead away, where tumbling walks it forward on its cluster corners instead of driving.

Simulation 3 · Transmission and the stall trigger

Drive the robot at the step. Watch the two candidate triggers — pitch and stall — and see which one ever fires.

Turn the phase hold off and watch the ride height wander. That is the 57 mm band from section 02 — and the terrain monitor starts reporting risers that are not there.

Going back down is not the same problem

Ascending, the riser stops the platform and the stall is an unambiguous you are here. Descending there is no such event: the beams see the drop while the wheels are still on solid floor, and a robot that keeps rolling drives off the top step. The last stretch is therefore dead-reckoned from geometry: 

creep = (tof_forward_offset + spot_ahead) − wheelbase/2 − margin
      = (0.180 + 0.290) − 0.130 − 0.05
      = 0.290 m

# Every term is measurable with a tape on the real robot. Nothing here
# depends on a threshold tuned by trial on a staircase.
Descent ships disabled (allow_descent: false). It has not been validated on hardware or in simulation and the failure mode is the robot falling down a flight of stairs. With it off the FSM refuses explicitly, and the MCP layer checks the whole route before setting off — so you find out in the kitchen, not on the landing.

05 — THE STACK

Eight packages, and one rule about the wheels

PackageDoesThe interesting decision
r2d2_descriptionURDF/xacro for the platform Every dimension derives from one YAML the world generator also reads
r2d2_simTwo-storey house, Gazebo bring-up World is generated; it refuses to emit stairs the robot cannot mount
r2d2_locomotionDrive, terrain, climb FSM Kinematics live in a ROS-free module so the maths is testable without ROS
r2d2_localizationEKF, regime gating, floors Regime switch applied through covariance, since the EKF can't be reconfigured live
r2d2_navigationNav2, routing, docking Docking servos on the live scan, so map error drops out of the loop
r2d2_perceptionVLA grounding Reports its own grounding quality instead of guessing a coordinate
r2d2_memoryLedger + pgvector JetStream is the truth; Postgres is a projection you can rebuild by replay
r2d2_mcpRobot as MCP tools + agent Tools return the real outcome, so the model learns what actually happened

Why MCP instead of asking for JSON

The previous planner put a JSON schema in the prompt, asked a model to emit one object containing a whole plan, repaired it with heuristics, and executed it open-loop. Three things were wrong, and tools fix all three.

One-shot JSONMCP tools
FeedbackPlan emitted before the first wheel turned Each call returns the real outcome and a reason
Parsingrepair_json may execute something else Schema-validated before anything moves
Capability driftPrompt carried the whole surface, grew forever Server describes its own tools; CI checks nothing goes stale
# What a failed navigation actually returns to the model now:
{
  "success": false,
  "reason": "a step too tall for the wheel clusters to mount is in the way;
             the route needs to avoid it",
  "distance_remaining_m": 1.84
}

The terrain monitor and odometry supervisor usually know exactly why Nav2 gave up, and that is far more useful to a language model than goal aborted.

06 — REPRODUCE

Run it yourself

In order. Each step has something you should actually see — if you do not see it, stop there rather than pressing on.

Step 0 · Check the geometry closes (30 seconds, no ROS)

Do this first after changing any dimension. It catches things a simulator only shows you as an unexplained failure to climb.

git clone https://github.com/Jayinaksha/agentic-bot
cd agentic-bot
pip install pyyaml xacro pytest pyflakes

python3 scripts/analyse_climb.py
python3 -m pytest -q src/r2d2_*/test

Expect 9 checks, 0 failed, 2 warnings (gait match and peak torque, both documented and deliberate); 275 tests passing.

Step 1 · Is the robot the right shape?

colcon build --symlink-install && source install/setup.bash
ros2 launch r2d2_description display.launch.py

Expect RViz with four tri-star clusters, a LiDAR on a short mast, four ToF frames at the corners and a trailing tail. If a cluster is inside-out, the phase offsets in the xacro are wrong.

Step 2 · Does it spawn and settle?

ros2 launch r2d2_sim sim.launch.py

Expect the robot drops ~90 mm and settles with two sub-wheels per cluster on the ground, chassis level, axle near 107.5 mm. If it sinks or jitters, that is contact stiffness — the first thing to tune.

This is where the real work starts. Contact-rich tumbling is exactly what simulators get wrong. The physics block is already set to a 1 ms step with a stiff solver for this reason, and you should expect to spend time on max_step_size, friction and solver iterations before it climbs cleanly.

Step 3 · Teleop on flat ground, then calibrate

ros2 launch r2d2_navigation house_stack.launch.py mode:=slam
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r cmd_vel:=/cmd_vel_nav

# Then measure the skid-steer scrub instead of trusting the 1.25 estimate:
python3 scripts/calibrate_slip.py

Expect the chassis to hold a steady ride height. If it bobs, the carrier hold is not working and every ToF threshold is void.

Step 4 · The staircase

# Drive to the foot of the flight (x ≈ 0.9, y ≈ 0.55), face +x, then:
ros2 topic pub --once /climb/request std_msgs/Bool "{data: true}"
ros2 topic echo /climb/state

Expect idle → align → approach → climb → settle → idle with a rise near 1.80 m. Untested — this is the step nobody has run, and the one worth reporting on either way.

Step 5 · Map both floors, then navigate

ros2 launch r2d2_localization slam.launch.py floor:=0
# drive the floor, then:
ros2 run nav2_map_server map_saver_cli -f ~/r2d2_maps/house_f0
# repeat with floor:=1, then switch to localisation:
ros2 launch r2d2_navigation house_stack.launch.py mode:=amcl

Step 6 · Memory and perception

docker compose -f src/r2d2_memory/docker-compose.yml up -d
python3 scripts/check_memory.py          # verify before wiring it in

export R2D2_NVIDIA_API_KEY=nvapi-...
ros2 launch r2d2_perception perception.launch.py

Step 7 · Talk to it

pip install mcp httpx
python3 -m r2d2_mcp.agent --dry-run "go to the kitchen and tell me what is on the table"

Expect the agent to call get_state and find_object for real, and refuse to move. Drop --dry-run only once the dry run reads sensibly.

Nav2 Jazzy or newer. The plugin names use the :: style Nav2 standardised on in Jazzy. On Humble every plugin here fails to load — silently, with no warning. python3 scripts/check_nav2_plugins.py --distro humble lists what would need changing.

07 — DEMOS

The footage that should live here

Two kinds of clip belong on this page. The simulations can be recorded on any machine with a browser, so they are recorded, below. The robot cannot: that needs Gazebo and a GPU. Those five slots stay empty, and the capture kit is ready for whoever has the hardware.

Recorded: the simulations

Headless Chromium drives the same sliders you can drag in sections 02–04, and records what it sees. Nothing is staged — the numbers in the readouts are computed live by the page's own code from src/r2d2_description/config/robot_params.yaml. Regenerate them with python3 scripts/record_sims.py.

S1 · The climb envelope, and where it fails simulation

Riser height sweeps from a door sill to 210 mm. Watch the reach circle — cluster circumradius + sub-wheel radius = 165 mm — lose the nosing, and the verdict flip from reachable to not. Then tread depth shrinks below a sub-wheel diameter and the second failure mode appears.

S2 · Why the ramp needs pitch correction simulation

The beam crosses a sill, a riser and a cliff, then the robot pitches −11.5° on the 12° ramp. The corrected reading holds at 0 mm; the naive one reads −96 mm and would call the whole ramp a cliff. This is the bug test_ramp_is_not_a_cliff is named for.

S3 · The trigger that could never fire simulation

Approach the riser with phase hold on: body pitch stays at 0.00° for the entire run, so a pitch-threshold trigger never fires — it would have aborted every climb. The stall detector accumulates its 0.6 s of evidence and fires instead. Turn the hold off and watch the ride height wander across the 57 mm band that invents phantom stairs.

These are recordings of the simulations, not of the robot. They show that the equations do what the text claims, which is worth something and is not the same as showing that the robot climbs stairs. Only the five slots below can settle that.

08 — CONTRIBUTE

Where the gaps actually are

Ordered by how much they would tell us, not by difficulty. The first one is worth more than the rest combined.

#GapWhy it mattersSize
1Run the climb in Gazebo and report what happens Settles the gait-match question. A recording of a failure is as valuable as a success A day, mostly tuning
2Tune the contact physics Everything downstream depends on the clusters behaving like clustersDays
3Validate descent, then enable it Without it the robot goes upstairs and stays thereDays, carefully
4A rigid-body contact simulator that can refuse a 0.50 m wall Two attempts failed falsification and were deleted; the bar is in the docsWeeks
5Measure yaw_slip_factor on real surfaces The 1.25 default is an estimate; the error is systematicAn hour
6Call the VLA once and check the response shape The request is verified against NVIDIA's API; the response never has beenAn hour
7Apply the schema and check the pgvector index lists=100 is a starting guess that needs dataAn hour

The one habit worth adopting

Every bug found in this project was in something that had been reasoned about rather than run. So the working rule here is: a check that passes tells you nothing until you have watched it fail. Before trusting any new check, break the thing it is supposed to catch and confirm it complains.

That habit caught a mistake immediately. Sealing the kitchen's hallway door did not make the reachability test fail — which looked like a broken test. It was a broken falsification: the kitchen has two doors, so the route through the living room survived. It also killed a climb simulator that cheerfully reported success on a 0.50 m wall. A subtly wrong simulator saying "it climbs" is worse than none.

Before you open a PR

python3 scripts/check_ci.py        # runs the whole workflow locally
python3 -m pytest -q src/r2d2_*/test
python3 scripts/analyse_climb.py
python3 scripts/generate_diagrams.py   # if you touched robot_params.yaml
